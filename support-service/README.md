# Hamvara Support — original implementation, v1

All support application source was authored for Hamvara. It uses browser and managed-server native APIs. No copied chat project, UI framework, model SDK, external chat widget, or third-party runtime package is bundled. The repository's existing pinned Wrangler CLI and CI tools are deployment/testing tools, not chat application code. Managed platforms and browsers have their own underlying software and licenses; this is not a claim that their entire infrastructure is proprietary Hamvara code.

## Boundaries and delivery status

- Public page: `https://hamvara.com/support/?lang=fa`
- Team inbox: `https://hamvara.com/support/admin.html`
- Launcher on homepage, preview, articles and online guides. Never injected into the MRP app.
- Separate Worker `hamvara-support`, separate SQLite-backed Durable Object. No ERP/D1/R2 binding, no customer-workspace tools, no existing-worker modification.
- Default AI OFF. Configuration alone must not imply successful deployment. The UI checks `/status`, fails closed and offers email/WhatsApp if unavailable. Public pages can deploy before backend activation.
- Browser-native polling (4 seconds visitor, 5 seconds inbox); not WebSocket delivery. Team online status expires after 75 seconds without heartbeat. Notifications only while the inbox is open; no background push/email delivery yet.
- This v1 responds to each question independently; it does not send full history to the model. Explain follow-up questions explicitly.

## Activation — do not paste secrets into chat or commit them

1. On your local machine, run `node support-service/provision-operator.mjs`. Choose an individual operator ID and name. Save the generated private key in a password manager. The key is entered only into the team inbox.
2. Create repository or production-environment secret `HAMVARA_CHAT_OPERATORS`. Its value is a JSON **array** containing the generated registry entry, e.g. `[{"id":"yahya","name":"Hamvara team","tokenHash":"<64 hex digits generated by the script>"}]`. For teammates, add separate entries and keep existing entries. Revoke access by removing an entry and deploying secrets again.
3. For AI, create `HAMVARA_CHAT_OPENAI_API_KEY` from your paid OpenAI API account. Never reuse an ERP access key or place an API key in frontend config. Choose an exact supported model ID in that account; no model is silently selected for you.
4. In GitHub Actions, run **Deploy Hamvara Support Manually** with `confirmation=DEPLOY-SUPPORT`. Existing `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` must have permission for a new Worker and Durable Object. The existing `production` environment gate is preserved. Enable AI only when API billing, key and model are ready. The operator registry is required even for AI, so escalation has a real destination.
5. The workflow tests, deploys ONLY `support-service/wrangler.toml`, and supplies secrets via stdin without printing values. First deployment is fail-closed until operator secrets exist. AI defaults false and has a 100-call/day global ceiling, at most 1600 output tokens/call. These are application caps, not a provider billing guarantee: also set an account budget.
6. Verify `https://hamvara-support.yahya-mazdarani.workers.dev/status`. `ready:true` means operator configuration exists; `online:true` requires a signed-in available operator. `ai:true` means configuration is present, not that model access/billing has passed a live test.
7. Open the inbox, enter the operator key, check Available. Start a test visitor conversation, send a guide question, verify actual delivery and a cited AI response, request a person, claim the conversation, reply, then delete the training conversation. No paid-model/live-delivery claim should be made before this test.

The configured workers.dev hostname follows the account's current suffix. If Cloudflare returns a different URL, update `support/config.js` and the `connect-src` CSP in both HTML pages before publishing.

## Data and security

Explicit storage consent is required; AI consent is separate and optional. Visitor tokens have 72 random UUID characters and only hashes are stored server-side. Operator tokens are generated locally, hashed in the server registry, and kept in page memory only by the inbox. CORS is restricted to hamvara.com and www.hamvara.com, but authentication and server rate limits enforce security independently of CORS.

Messages render as text, not HTML/Markdown. SQL values use bound parameters. Messages are limited to 1800 characters and 100 per conversation. Session, IP and global limits are enforced in durable storage. Idempotency IDs prevent duplicate submissions. Human takeover invalidates a pending model response; returning to queue never silently re-enables AI. Individual operator ownership prevents competing replies.

Active data is removed after 30 days from conversation creation through requests and a scheduled Durable Object alarm, or immediately through authenticated deletion. Infrastructure backups/logs are subject to provider retention. Rate-limit counters contain hashed IPs and are purged on subsequent requests. No message contents or secrets are logged by application code.

AI gets the selected product’s complete short guide in authored order (6 SKU or 10 MRP chapters per language; both when explicitly requested), no tools, and no access to ERP data. This preserves prerequisites that isolated top-three retrieval omitted. More guide context and the larger output cap may increase token use; the daily call cap is unchanged. Responses must reference known excerpt IDs; unknown sources, invalid JSON, timeouts, errors, out-of-scope or pricing questions hand off. A citation/schema check cannot prove every generated statement is correct; real multilingual evaluation is required before expanding scope. `store:false` disables Responses API application storage; it does not promise zero provider logging.

## Maintain and test

```sh
python support-service/build-knowledge.py
node --test support-service/test/*.test.mjs
```

Knowledge is generated from our own `_site-preview-source/manuals/*.json`. Review these sources, rebuild, and deploy the support service when guides change. Tests use built-in Node APIs and real in-memory SQLite; no model charges or customer data. Existing CI browser checks additionally verify the public fallback and widget rendering. No runtime dependencies are installed in this folder.

## Reviewed workflow responses

Broad SKU Bridge import plus review/export questions use an original, reviewed nine-step answer in EN/FA/TR, with all six guide sources. This route runs only inside the existing opted-in assistant flow and preserves handoff and quota controls; it makes no OpenAI request. It is labeled as a reviewed guide. Narrow questions still use the model with product guide context. Keep `src/reviewed-workflows.js` synchronized with the product guide when controls change. The call counter remains a conservative assistant-turn cap, including reviewed responses.


## Abuse controls (application layer)

Additional limits: 600 public requests/minute across IPs; 10 failed operator
credentials per IP per 15-minute fixed window; 12 assistant turns/conversation/day;
20 assistant turns/IP/day; at most 5 concurrently processed assistant answers per
Durable Object instance. Existing daily global AI, message and session limits stay
in force. Rate windows are fixed, so boundary bursts are possible. Shared office
IPs share limits. Operator routes do not consume the public global request budget.
HTTP 429 includes Retry-After. Exhausted AI budgets or concurrency transfer the
conversation to the human queue without calling the provider. Reviewed answers
also consume the conservative assistant budget.

Emergency: set Worker variable CHAT_ACCEPT_NEW_SESSIONS=false to pause new chats;
existing conversations and the operator inbox remain accessible. Remove it or set
true to reopen. CHAT_AI_ENABLED=false disables AI provider calls. These are Worker
variables, not frontend secrets; preserve the existing manual deployment gate.

These limits do NOT identify humans and are NOT an edge DDoS defence. Requests
still reach the Worker/DO and can incur infrastructure cost; distributed attackers
can exhaust public quotas and deny chat to legitimate visitors. CORS is not bot
authentication. The Turnstile layer below requires a configured Cloudflare widget and secret.
Additional edge rules must target the actual Worker hostname.
Turnstile integration is included below; account-level WAF/edge protection is
not configured by this code. Do not imply whole-site/ERP protection from support-only limits. No external
runtime package or open-source implementation was added.


## Turnstile activation

Production config requires Turnstile for every new visitor session. GitHub secret
HAMVARA_CHAT_TURNSTILE_SECRET_KEY is uploaded as Worker TURNSTILE_SECRET_KEY before
the manual deployment. The public sitekey is in support/config.js. Configure the
widget for hamvara.com, Managed mode, no pre-clearance. The application checks
Siteverify success, exact hamvara.com/www.hamvara.com hostname and support_start
action. Missing, reused, expired or invalid tokens are rejected; unavailable
verification fails closed. No verification tokens or secrets are stored in chat
records or application logs. Existing bearer-authenticated conversations and
operator login are unaffected. Turnstile is a hosted Cloudflare service, not a
copied open-source implementation; integration code is Hamvara-authored.

The browser loads the widget only for a new conversation when the backend reports
verificationRequired=true. During rollout an old backend does not enable the new
start form; deploy the support workflow after Pages publication. The widget resets
after a failed start and clears expired tokens. Email/WhatsApp remain available if
verification cannot load. Frontend changes include the required CSP allowances and
EN/FA/TR privacy notices. Local tests mock Siteverify and widget callbacks; a real
browser test after deployment must confirm the actual Cloudflare keys/domains work.
This does not replace edge DDoS controls or protect unrelated ERP endpoints.


## Session quota correction

Successful verified sessions now have distinct counters: five per IP per fixed
15-minute window and twenty per IP per UTC day. The global 200/day limit remains.
Before verification, separate attempt limits allow ten per IP/minute and 120
across IPs/minute; existing public request limits still apply. Failed verification
does not spend the successful-session allowance. The quota is checked again after
all asynchronous verification/hash work, immediately before insertion, so parallel
requests cannot pass the same stale quota check. Old five-attempt/day counters are
no longer used; no conversation data or counters are deleted. This is an explicit
policy change, not an operator bypass. AI budgets remain unchanged. Rate-limit
responses now include the actual fixed-window wait in Retry-After and JSON
retryAfter; the start form displays the rounded-up minutes in EN/FA/TR.
